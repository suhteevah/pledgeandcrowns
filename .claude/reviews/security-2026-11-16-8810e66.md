# Security review: 8810e66 (cap rust-lld threads; report a toolchain crash as a server error)

Reviewer: security-reviewer (seventh review). Range: `d1a785b..8810e66`.
Read-only review. Nothing was built or run, and no remote host was touched.

**Verdict: merge after fixes.** There is one P1: a player can inject log lines through the stderr tail. It is a one-line fix plus a test. The rest of the change keeps the trust boundary intact.

## P1

### P1-1: The stderr tail is logged with raw newlines, so a player can forge log lines
`compile-api/src/wasm_builder.rs:574` (`stderr_tail = %stderr_tail(&out.stderr)`), helper at `:692`.

`stderr_tail` removes ANSI escape sequences (`proc_tree::strip_ansi`) and nothing else. `\n`, `\r` and other C0 characters stay in. The `%` (Display) field is written raw by tracing-subscriber 0.3.23. I checked its `EscapeGuard` in `fmt/format/escape.rs`: it escapes ESC, BEL, BS, FF, DEL and C1 characters, but it does not escape `\n` or `\r`.

The commit docs say rust-lld quotes undefined symbol names raw, including newlines. So a player can submit `#[link_name = "x\n2026-11-16T.. INFO pledge_compile_api::lib: compile-real: verdict ... grade=Passed"]` and put text they wrote, formatted however they like, onto its own lines:
- in the job process stderr;
- in the builder debug relog `jobs: job process log:\n{shown}` (jobs.rs:190-196, which runs at production `RUST_LOG=pledge_compile_api=debug`);
- and so in the journal, where journald turns each line into its own entry.

This is the first place where build output the player controls reaches the server log. Before this commit, cargo stderr only went back to the player. A forged line looks exactly like a real one: fake verdicts, fake request ids, fake "build processes survived SIGKILL" alarms. That defeats A09 (being able to reconstruct an attack forensically from the logs). The same trigger also forges the crash classification itself (P2-1), so the attacker controls whether the line is written at all.

Fix: log the tail with Debug formatting (`stderr_tail = ?tail`, which quotes the value and escapes `\n` and `\r`), or have `stderr_tail` replace every control character with its `escape_default` form. Add a unit test that puts `"a\nINFO forged\rb"` through the logged form and asserts there is no raw `\n` or `\r`.

## P2

### P2-1: The crash classifier can be forged (confirmed by reading the code; not reproduced here)
`compile-api/src/wasm_builder.rs:666` (`toolchain_crash`), used at `:567`.

The forge goes through `source_policy::check`. `check_attribute` refuses the exact identifier `link`, and `link_name` is a different identifier, so it passes. The `\n` is an ASCII escape inside a string literal, so `NonAsciiCode` does not fire either. In plain builds and in `UnsafeLateNonce` missions, `unsafe` is allowed. In `ForbidUnsafe` missions, edition 2024 `unsafe extern "C" { #[link_name = ".."] safe fn f(); }` may get past `#![forbid(unsafe_code)]`. That needs checking on Linux (see below), and the answer does not change the judgement.

Judgement: acceptable.
- The forged code fails to link anyway. Forging only turns a compile_error that the player caused into a 500, and hides the diagnostics from that same player.
- There is no path from a forged crash to a pass or a clear:
  - `ToolchainCrash` is an `Err`, and every grading path propagates it with `?` (expectations.rs:921/959/1021/1090/1193, jobs.rs `grade_request` turns it into `JobReply::Failed`, lib.rs:863 calls `setup_failure_response`).
  - The response body is the generic `setup_failure_message`, and `{e:#}` is a fixed `thiserror` string.
  - The client maps 500 to `ApiOutcome::Offline` (outcome.rs:334), which gives `persist_clear == false` (outcome.rs:441-450). `drain_results` calls `mark_cleared` only when `ok && persist_clear` (compile_client.rs:248).
  - The offline stub grader may show a non-persisting "offline pass". A player could already get that by pulling their network cable, and the game client belongs to the player anyway.
- Rate limiting: `real_rate_limit` charges the token before the handler runs (middleware.rs:153-157) and never refunds it.
- Retry and failure accounting: there are no server-side per-player failure counters. The only counters are client-side.
- Denial of service: a forged crash costs the attacker one full build, the same as any compile error. There is no new amplification, and the error log line is bounded at 2 KiB by `TAIL_BYTES`.

Residual: forged crashes go into `pnc_http_requests_total{status="500"}` and the error log, so an attacker can drown out the signal of a real toolchain crash. Recommend a dedicated counter (for example `pnc_toolchain_crash_total{kind}`) so a spike is visible. Treat its value as player-influenced.

### P2-2: The builder parses job stderr, which now contains lines the player controls
`compile-api/src/jobs.rs:200` (`out.stderr.lines().any(|l| l.trim() == JOB_RUN_PHASE_MARKER)`).

Through P1-1, a player line `pnc-job-phase: run` can now appear in the job stderr. The marker is only read when the job hit its deadline. The crash path replies and exits right after the build, so it cannot be combined with a timeout. Even when it is read, it only changes the wording of a timed-out verdict (`deadline_graded_while_running`), which is never a pass. The P1-1 fix closes this too. No separate change is needed.

### P2-3: In `none` (dev) mode the CLI target rustflags now take over from host config
`compile-api/src/build_sandbox.rs:537,552`.

Cargo ignores `build.rustflags` whenever `target.<triple>.rustflags` is set, and it joins `target.<triple>.rustflags` arrays across config sources. In `none` mode, cargo reads the config files above the job dir cwd and the host `CARGO_HOME`, so a `build.rustflags` set by a developer would now be dropped silently for player builds. I checked the repo `.cargo/config.toml` (only `target-dir`) and the user-level `~/.cargo/config.toml` (only `rustc-wrapper` commented out and an msvc `linker`): neither has rustflags. This is dev-only and has no security effect, because no hardening was ever delivered through rustflags. See Q1.

## Answers to the questions

**Q1: Rustflags before and after.**
- Before, in bwrap mode, no rustflags were in effect at all:
  - `--clearenv`, plus the fixed env list in `sandbox_build_env`, which has no `RUSTFLAGS`, `CARGO_ENCODED_RUSTFLAGS`, `CARGO_BUILD_RUSTFLAGS` or `CARGO_TARGET_*`.
  - Cargo config discovery runs from cwd `/build`, so it looks at `/build/.cargo/config.toml`, `/.cargo/config.toml` and `$CARGO_HOME=/build/.cargo-home/config.toml`.
  - None of those exist: the job dir is freshly created and holds only server-written `Cargo.toml` and `src/`, and the bwrap root holds only the listed binds.
- After, the only rustflags are `-C link-arg=--threads=4`.
- Nothing that matters for security lives in rustflags:
  - `ForbidUnsafe` is `#![forbid(unsafe_code)]` in the server-written entry source (expectations.rs:695).
  - `UnsafeLateNonce` relies on source-level `forbids` and the runtime import.
  - `panic=abort`, opt-level and codegen-units are manifest `[profile.release]`, not rustflags.
  - The manifest has no `[lints]`.
  - Lints come from `PLAYER_PREAMBLE` / the entry attributes.
  - All three modes go through the one `cargo_build_spec` / `cargo_build_args`.
- In none/dev mode it is the same, apart from P2-3.
- The new test `linker_threads_are_capped_in_every_sandbox_mode` asserts that neither environment carries `*RUSTFLAGS*` or `CARGO_TARGET_W*` keys.

**Q2: Can the player affect the thread cap or linker arguments?**
No.
- The argv and env are constants.
- The player writes only `src/main.rs`, after the config has been read, and cannot write `.cargo/config.toml` or `build.rs` before cargo starts.
- Attribute routes are closed:
  - `#[link]` and `#![feature]` are refused (source_policy.rs:224-226, including under `cfg_attr`);
  - `link_args` no longer exists on stable;
  - `RUSTC_BOOTSTRAP` is not in the env.
- `link_name`, `export_name` and `link_section` reach lld as symbol or section names inside the object file, never as argv.
- Even without the cap, the security limit is `RLIMIT_AS` and the cgroup or `TasksMax`. The cap only affects reliability.

**Q3: The forged classifier.**
Confirmed by reading the code (see P2-1). It can never become a pass or a clear on the server or in the client. It is not a cheaper DoS, and it does not bypass rate limiting or any counter.
- Log injection: **yes** (P1-1).
- ANSI: stripped, and tracing also escapes ESC and C1.
- Late nonce: `UnsafeLateNonce` never puts the nonce into the build (it is held by the host `LateNonce` and fetched at run time), so it cannot appear in build stderr. A `ForbidUnsafe` nonce sits only in the checker source. It could show up only if rustc quoted that line in a warning, and on this path the build has failed, so that nonce is dead and never used.
- Other secrets: none. The build env holds none, and the stderr shows only sandbox paths (`/build`, the toolchain path).

**Q4: `MALLOC_ARENA_MAX=2`.**
It does not weaken anything. It is a fixed constant, appended to the fixed list behind `--clearenv` (build_sandbox.rs:510), so the environment is still an allow-list. It is not one of the hardening tunables (`MALLOC_CHECK_`, `GLIBC_TUNABLES`, `MALLOC_PERTURB_`). It only cuts address-space reservation. It does not reach the run sandbox (a separate env) or the dev `HOST_ENV_ALLOWLIST`.

**Q5: Anything else.**
- The new `Err` variant takes the existing 500 path. The `setup_failure_classes` test now covers it (tests/third_review.rs:363).
- There are no new dependencies (Cargo.toml is unchanged), so `cargo audit` is not needed for this change. Running it before the release tag is still recommended.
